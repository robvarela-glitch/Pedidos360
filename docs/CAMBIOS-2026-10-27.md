# Cambios 27/10/2026 — preparación Evaluaciones 3 y 4

## Qué cambió

### Seguridad (todos los servicios)
- `config/JwtSecuritySupport.java` (nuevo, igual en los 7 servicios): firma (JWKS del tenant), expiración, issuer v1/v2 del tenant, audience de la API (`api://<client-id>` o `<client-id>`), scope `access_as_user`, roles `Admin/Operador/Cliente` y `DEFAULT_ROLE`.
- **Se resolvió la inconsistencia de audiences**: antes BFF esperaba `api://ms-pedidos360-bff` y Orders `api://ms-pedidos360-orders`, y Entra ID emite tokens para `api://bd954135-...`. Ahora todos validan la misma API.
- BFF: reglas explícitas método+ruta, `denyAll` para lo demás, CORS por orígenes, `GET /api/me`, ruta a `rabbitadmin`, timeouts y 503 si un servicio interno no responde.
- Microservicios: `@EnableMethodSecurity` + `@PreAuthorize` por rol.

### Negocio
- Orders: cliente = claim `oid` (se ignora `customerId` del JSON), precios desde Catalog (`CatalogClient`), validación de stock y producto activo, filtro por dueño (403 para pedidos ajenos), transiciones de estado válidas (409 si no), cancelación por el cliente solo en CREADO.
- Catalog: campos `brand`, `category`, `imageUrl`, `specifications`; carga inicial en Oracle (`CatalogSeeder`); 409 por SKU duplicado; solo productos activos para clientes; publica `product.*`. Se agregó `spring-boot-starter-validation` (faltaba en el pom).
- Notify: notificaciones filtradas por dueño.
- Report y Audit: consumen RabbitMQ (antes Kafka). Audit registra pedidos **y** productos.

### RabbitMQ (rúbrica)
- Topología centralizada en `application.properties` (`pedidos360.rabbit.*`) + `RabbitTopologyProperties`.
- Exchanges: `pedidos360.orders.direct` (direct), `pedidos360.events.topic` (topic), `pedidos360.dlx` (dead-letter).
- Colas: `pedidos360.notify.orders`, `pedidos360.report.orders`, `pedidos360.audit.events`, cada una con `.dlq`.
- `ManualAckHandler`: ACK manual, errores no recuperables → DLQ, recuperables → 3 intentos → DLQ, logs `[ACK] [RETRY] [DLQ]`, simulación de fallos por header para la demo.
- Nuevo **`ms-pedidos360-rabbitadmin`** (puerto 8086): API REST de colas, exchanges, bindings, nodos y publicación de prueba, con validaciones y recursos protegidos.
- Kafka queda **opcional** (`KAFKA_ENABLED=true` + `--profile kafka`).

### Infraestructura
- `docker-compose.yml`: clúster RabbitMQ de 2 nodos, nuevo `ms-rabbitadmin`, frontend con nginx, healthchecks, `JAVA_TOOL_OPTIONS` con IPv4 y límite de memoria, puertos internos solo en `127.0.0.1`, credenciales por `.env`.
- `infra/aws/setup-ec2.sh` y `infra/aws/create-api-gateway.sh` (HTTP API + autorizador JWT + rutas explícitas + CORS).

### Frontend
- Sin datos simulados: servicios HTTP reales (`orders`, `catalog`, `backoffice`, `rabbit-admin`, `auth`).
- `config.json` en tiempo de ejecución (misma compilación para local y nube).
- MSAL pide el scope de la API y el interceptor agrega el token a `/api/*`.
- Vistas por rol (menú, rutas con `roleGuard`, acciones en detalle de pedido), nueva página **Mensajería** (Admin).
- Se eliminó `core/guards/auth-guard.ts` (leía un token de localStorage y no se usaba).
- `Dockerfile` + nginx (reenvía `/api` al BFF en local).
